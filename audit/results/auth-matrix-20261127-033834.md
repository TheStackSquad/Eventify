## Next steps (where to look)

- **AUTH-T9 [FAIL]** a refresh token past its stored expiry is refused: F405: RefreshToken never reads refresh_tokens.expires_at, so the 24-hour life stored for a session login is ignored and only the 30-day JWT expiry applies. Refuse a token whose stored expiry has passed.
- **AUTH-T10 [FAIL]** a session that began more than 30 days ago cannot be refreshed: F406: the 30-day absolute limit is measured from the created_at of the current token, which restarts at every refresh, so a session never ends. Measure from the first login of the chain.
- **AUTH-C2 [INFO]** the Secure flag on the session cookies: F414: Secure depends on COOKIE_SECURE (default off). Production must set it, and logout must clear cookies with the same flags.

## Claims supported by this run

- A sign-up cannot choose its own role, and invalid sign-ups are rejected.
- A sign-up cannot choose its own user id.
- A duplicate email is refused cleanly, in any letter case, and login works in any letter case.
- Login answers never expose secrets, and a wrong password and an unknown email look the same, in answer and in time.
- Accounts lock after five wrong passwords and unlock after ten minutes, whatever the time zone of the server.
- Session cookies are HttpOnly with SameSite, and state-changing requests need a matching CSRF token.
- Forged, unsigned and re-signed tokens are refused.
- Logout kills the access and the refresh token, whichever way the client authenticated.
- Refresh rotates both tokens and needs a session.
- Reusing an old refresh token ends the whole session, and simultaneous refreshes never split a session.
- Only the named website origin receives CORS permission.

## Not demonstrated in this run

- A refresh token cannot be used past its expiry, and a session ends at its absolute limit. (needs: AUTH-T9, AUTH-T10)

## Limits of this evidence

- One backend process on one machine. Multi-instance behaviour is not exercised.
- Paystack test mode and one payment channel. Live mode and other channels may behave differently.
- The webhook URL saved in the Paystack dashboard cannot be read by this script; T1.2 confirms it indirectly.
- This run uses a local backend and the rig database; no tunnel is used.
- Rate limiting is not exercised: the limiter skips localhost, so those checks need rig mode (a later piece).
- Expiry and session-lifetime checks move rows back in time in the database, because waiting 30 days is not possible.
- The password-reset flow and the rate limits (rig mode) are covered by later pieces.
